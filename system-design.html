3. 架构设计

3.1 分层结构

核心原则：内核纯逻辑、视图只做绑定、页面只做装配。内核不碰 DOM，才能在 Node 里直接断言。

① 页面层
*.html：只做结构装配（topbar / panel / stage），引入 CSS 与对应 app.js。共 12 页。
② 视图层
js/<lab>/app.js：DOM 事件绑定、Canvas 绘制、读数刷新、动画循环。唯一允许操作 DOM 的层。
③ 内核层
js/<lab>/core.js：纯函数与状态机（求解器 / 积分器 / 布局引擎 / 投影器），暴露 window.<Name>Core，无 DOM 依赖。
④ 数据层
js/formula/data.js、知识目录 BOOKS/CHAPTERS、资源 TOOLS、案例 CASES：数据与逻辑分离，便于增删条目。
⑤ 质量层
verify-*.js（Node 直跑内核）+ scripts/test-all.js（聚合）+ scripts/check-pages.js（断链体检）。

3.2 模块边界与接口契约

内核导出的关键函数自检
TerrainCore高程场合成、等高线、剖面采样、3D 投影verify-terrain（≈43）
CircuitCore节点装配、高斯消元、非线性迭代、支路电流verify-circuit（≈11）
MechCoreanalyze(doc)、createRun(doc)、inclineOrigin、findContactverify-mech（33）
MolCore分子/晶体数据、makeProjector、crystalBondsverify-mol（608）
MiniTeX / FormulaCoreparse→layout→draw、31 条关系 calc/readsverify-formula（633）

契约约定：内核一律 IIFE 挂 window.Xxx，并在 Node 下兼容 module.exports； 自检通过共享 window 桩按序 require 两个模块即可运行。不改这条约定，自检就不会失效。

4. 关键取舍

4.1 多页（MPA） vs 单页应用（SPA） vs 引入构建

方案优点代价结论
MPA（现状）零构建、file:// 直开、单页互不影响、调试直观页面骨架重复、导航需手写采用
SPA + 路由共享 shell，切换无刷新需 hash 路由模拟，file:// 下易踩坑；首屏 JS 变重不采用
Vite/框架构建工程化完善、生态好破坏"零依赖 + 双击即开"，需要 node 环境与产物目录否决

理由：硬约束是"离线直开"。任何需要构建或服务器的方案都会牺牲这一条，收益（消除重复）可用更轻的共享脚本解决。

4.2 消除 6 页重复骨架的三条路

方案做法风险建议
静态复制（现状）每页手写 topbar改一处要改 6 处，易漂移暂用
shell.js 注入每页只留 <header data-lab="mech">，脚本渲染统一顶栏JS 未跑时顶栏空白（需 <noscript> 兜底）P1 推荐
Web Component<lab-topbar> 自定义元素file:// 下模块加载与旧浏览器兼容成本更高备选

4.3 移动端适配的三条路

方案做法代价结论
CSS media query≤900px 侧栏改为上置、画布降高无 JS 改动，风险最低本轮采用
抽屉式面板侧栏收起为抽屉，按钮唤出需改 6 页结构 + 状态管理P1
独立移动布局另做一套移动端页面维护双份，成本翻倍否决

6. 风险与限制

R1 · file:// 的 fetch 限制：任何"运行时读取本地文件"的案例（如 Logico 的组件注册表）在 file:// 下会被 CORS 拒绝，必须走 npm run serve。当前案例库已把这类排除或标注。
R2 · 无构建 = 无打包优化：页面数量增加时，重复骨架会线性放大维护成本。这是 P1-1 的直接动因。
R3 · 自检口径不完全统一：地形与电路只输出"全部通过"，断言数按 ✓ 计数估算（表中以 ≈ 标注），精确计数需改这两个脚本的输出格式。
R4 · 第三方案例的许可差异：ai-cases/ 中 physics-sim 为"保留所有权利"，仅作本地学习参考，不得再分发；MIT 来源可自由使用。
R5 · 数值模型边界：力学仅平动模型，不处理转动与物体间碰撞；分子为刚性球棍模型。教学演示够用，工程仿真不够用。
